Method and how to read the results

  • Codecs: Linux 6.12 LZ4 is the kernel's lib/lz4, called as LZ4_compress_fast and LZ4_decompress_safe. Its compressor is based on LZ4 1.7.3 and its decompressor on LZ4 1.8.3, with later kernel fixes. LZ4 1.11 is upstream v1.11.0.
  • Build: All codecs use -O2 -mgeneral-regs-only -mno-red-zone -fno-strict-aliasing -fno-stack-protector -fno-tree-vectorize -mtune=generic, plus -falign-* to fix code layout. memcpy is rep movsb, as in the kernel on FSRM CPUs.
  • Runs: Values are medians of 31 rounds with a warm cache and 21 rounds with eviction, pinned to one core, with pages in shuffled order. Binaries, source and anonymous memory are 20–64 MiB. The five 4 MiB data sets (HTML and prose, .rela.dyn, and the extreme group) have very short passes, so they use 15 rounds of 41 passes (warm) or 11 rounds of 15 passes (eviction). Repeating the same pages may let branch predictors learn them.
  • Noise: Identical binaries differed by up to % with a warm cache and % with eviction. Those maxima come from 4 MiB data sets; at 20 MiB or more the spread is about 1%. Treat smaller differences as ties.
  • Absolute speeds: Other work was running during the measurement (load average 3–6). MiB/s values depend on the environment, so read them as ratios between codecs measured under the same conditions.
  • Stack bias: Binary name length alone moved decode speed by up to 7% for identical code. Names are therefore equal in length, and each round uses a random stack offset shared by all codecs.
  • .rela.dyn: This is exe.bin, previously labelled an executable corpus. It is the first 4 MiB of containerd and nearly all relocation data, not machine code. Use the binary group to judge code.
  • Limits: Nothing here was measured in a running kernel's zram. The only CPU is Zen 4, so Intel and aarch64 are untested. Anonymous memory was captured from Python and Node processes and is not real swap content. Video, prose and the synthetic data are 4 MiB each.
